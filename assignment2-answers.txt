Q2
The TRAPFRAME page, which holds the user process's registers during a trap, is necessary because RISC-V hardware does not switch page tables when a trap occurs from user space. When a trap happens, the initial handler, uservec, begins executing immediately using the current user page table. To safely store all 32 user registers in the process’s dedicated trapframe in memory, the virtual address used for this operation (TRAPFRAME or 0x3fffffe000) must be valid in the active user page table. If uservec tried to push registers onto the kernel stack or into the kernel’s proc structure—both located at high kernel virtual addresses—these accesses would fail because those addresses are usually not mapped in the user page table, causing an exception or panic. Therefore, the dual mapping of the TRAPFRAME (accessible in both user and kernel page tables) is crucial for saving process state before the operating system safely transitions to full kernel execution.

Q3
The TRAMPOLINE page is needed because, similar to the TRAPFRAME, the trap handler entry point defined by stvec must be mapped in the user page table; RISC-V hardware does not switch page tables during a trap. In theory, this dedicated TRAMPOLINE mapping could be removed if the kernel mapped all of its memory into every user process’s page table, restricting access by clearing the PTE_U flag. This would allow the trap handler to execute immediately under the user page table without a separate trampoline. However, xv6 avoids this approach to maintain memory isolation and reduce security risks from accidental misuse of user pointers. Instead, it opts for the simpler and safer solution of using a dual-mapped TRAMPOLINE page.
